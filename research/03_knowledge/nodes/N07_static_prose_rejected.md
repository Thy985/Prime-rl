# N07 — 静态散文假设被否：文字不是控制信号

## 1. 这里发生了什么

把 H_D 的行为指南写成**一段静态行为描述**放进 H_A 的系统提示里
（H_A-prime），其它什么都不变。结果：H_A-prime 1/16、H_A 2/16、
H_D 7/16。静态散文**一点都恢复不了** harness 的差距——「告诉它怎么做」
和「每回合按当前阶段提醒它」是两种完全不同的东西。

## 2. 为什么走到这里

N06 确认效果真实。立刻冒出一个廉价解释：H_D 不过就是「提示词写得好」。
如果是这样，把同样的话写进 system prompt 就能复现——这个控制很便宜，
值得先做（D11 把 H_A-prime 排在三个子研究之首）。

## 3. 这里真正的问题

- Q1: 效果是不是「提示词写得好」造成的？
- Q2: 同一段行为文本，静态放 vs 每回合注入，是否等价？

## 4. 我原来怎么想

以为把行为说清楚放进 system prompt，至少能恢复一部分差距——
毕竟文字是一样的。

## 5. 我做了什么

构造 H_A-prime：H_A + 一段静态行为段落（`SWE_REAL_H_A_PRIME=1` 由
taskset.py 注入）。同一批实例、同预算、同模型，和 H_A/H_D 对比。
n=16 per arm（base+topup 池化）。

## 6. 得到了什么

大白话：**光把「你应该先看、再改、再检查」印在说明书上，模型不会照做。
得在每个决策点、以当前阶段的身份再提醒一遍，它才真的那样分配动作。**

## 7. 这改变了什么理解

原来：可能只是 prompt 措辞问题，改文字就能复现。
现在：**被否。** 1/16 vs 7/16——静态 instruction 文本不是控制信号。
「同样的文字，注入方式不同，是不同变量」——这为 N10/N11 的
「注入是机制」铺路。

## 9. 专业术语

- static instruction：我的理解——一次性放在提示里的行为说明；
  本项目含义——H_A-prime 的注入方式，被证明无效。
- system prompt：我的理解——对话开始时的固定上下文；
  本项目含义——放静态散文的地方；不是控制面。

## 10. 可迁移的东西

「写清楚 ≠ 会执行」（instruction 与 control 的区别）：
对任何 agent 行为目标，问一句「是每回合提醒，还是开头说一次」——
两者在效果上可以天差地别。适用于 prompt 工程、RLHF 目标设计。

## 11. 还不知道什么

- known：静态散文恢复不了差距（1/16 vs 7/16）；32 eps 里 0 次测试运行。
- inferred：注入的**时机/身份**才是变量，不是文字内容。
- open：如果静态散文是超大模型/更强模型呢？未测——当前 claim 不含它。
